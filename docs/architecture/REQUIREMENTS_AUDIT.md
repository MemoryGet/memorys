# V1 需求覆盖与证据审查

## 1. 审查口径

原始范围包括总体方案的20个模块、注册替换机制、数据归属、权限发布流程，以及五类前期成果。用户最新优先级为“先把架构设计好”。本审查分别标记设计覆盖与实现证据，不把未启动的产品实现算作设计完成，也不因文档齐全宣称最终架构验收已通过。

本文记录当前文件中的设计证据。标准契约关系校验和内部装配内核已实现并通过包测试，文件级离线配置检查已运行；正式部署接入、真实适配器、迁移和性能证据仍缺失。2026-10-12的逐项结论见 [架构验收报告](ACCEPTANCE_REVIEW.md)，总目标保持未完成。

## 4. 架构验收条件审查

| 原始条件 | 如何证明 | 当前判定 |
|---|---|---|
| 底层替换后界面/伙伴正常调用兼容 | 同一客户端完成前后场景并对照结果 | 缺运行证据 |
| 同一权限、发布、引用、故障、幂等测试通过 | 对每个真实实现运行公共契约和场景测试 | 缺运行证据 |
| 数据可导出迁移验证回退 | 包含新写入和墓碑的完整演练 | 缺运行证据 |
| 重建后可追溯原件/版本/位置 | 冻结标准Block与历史citation对照 | 有设计，缺运行证据 |
| 能力不足/契约错误/配置错误明确暴露 | schema、语义装配、真实健康失败测试 | 结构、离线语义和内部内核失败路径通过；正式部署及真实健康证据缺失 |
| 同一评测集比较召回/准确性/延迟/成本 | 固定语料、模型、硬件和负载报告 | 仅有指标方案，缺评测集和报告 |

## 5. 当前设计收敛与下一步

已确定：模块化单体、平台权威内容、稳定业务契约、受控适配器注册、允许重启替换、默认暂停写入迁移、发布指针与索引分阶段提交、KB/文档两层代际、有限反思、统一REST/MCP应用服务。

实现选择待收敛：WeKnora能否保留人工审核后的标准内容与来源；其过滤规模和上下文扩展边界；中文全文后端；具体模型与负载阈值；各候选的固定版本及许可证/依赖清单。先做源码/API核验和小范围兼容试验，再选择生产适配器，不以功能数量扩大组件堆叠。

下一步设计工作优先补齐已选组件的能力证据和正式契约产物。业务实现继续遵循用户的架构优先要求。该文档不缩减原始目标，也不代表产品或完整架构已验收。
