## 有界诊断执行

```powershell
python docs/architecture/check_postgres_wsl.py --major 16 --port 55432 --governance-repro-rounds 20
```

次数限定0至50，默认0仍运行完整流程。诊断模式使用不同默认报告名，禁止覆盖标准完整报告。通过AKOS_TEST_GOVERNANCE_REPRO=review-renew显式选中检查点；未知模式拒绝。checkpoint到达时只输出diagnostic_only=true及审批/首次租约样本，不输出完整go_repository_proof。完整模式明确拒绝诊断输出，时钟异常也不能满足通过条件。

临时实例、固定本地端口、私有数据库及所有权marker由现有验证器创建；仅这个已确认归属的临时实例可在下一轮删除固定akos_withdraw_v1模式并重新应用原型SQL。模块、命令和每轮上下文均由新Go进程建立，逐轮遇到首败即停止。没有接管已有PG进程，没有修改用户数据库，也没有修改系统时钟。

目前实际有界运行很快在第一轮捕获失败，尚未取得这一新模式下连续多轮成功重建的实库证据；不能把最大次数配置当作已完成20轮。前四轮完整采样是增加诊断模式之前的历史运行。

新增单元检查覆盖次数边界、模式显式选择、诊断与完整报告分离及不稳定时钟不能通过。另有[实际CLI负向检查](evidence/governance-report-separation-review.json)证明指定标准报告路径时提前退出，原完整报告的字节摘要不变。

## 墙钟观测与验收门禁

离线Go探针在自身生命周期内比较两条本地观测：UTC墙钟增量与time.Time中保留的单调增量。每2毫秒采样一次，并在结束时额外采样；正常调度停顿使两者一起增加，不当作时钟跳变。观测总偏差和相邻步变，超过100毫秒就标记unstable，最多保留4条详细事件及总计数；停止时同步等待观测goroutine结束。

100毫秒是本地诊断阈值，不是新生产SLO、令牌容忍窗口或租约宽限。正反4秒跳变、逐渐累积偏差、普通10秒调度停顿、证据上限及停止/回收均有确定性单元覆盖。

即使业务检查点已经成功到达，只要该次进程观测到时钟异常，进程仍失败，Python记录environment_clock_unstable=true及原业务结果。已捕获的4.18秒运行正是这种情况：checkpoint已完成，但不能输出诊断通过，更不能伪装完整通过。失败报告同样记录源码清单和执行期间是否变化，不丢失原始失败。

这只是该进程采样窗口内的相对时钟观测：没有检测到步变不等于UTC正确，也不能证明其他节点/发行者同步。观测器没有用于替换数据库租约时间、审批时间或认证器；当前部署/业务适配器的时间语义保持原样。

## V1时钟前置条件与模块边界

1. 本地操作预算依赖单调计时；持久租约、签名凭据及审计的绝对期限依赖可信UTC。两者不能混为一个“剩余时长”。
2. Go与PG数值一致不代表独立UTC正确，两者可能共享同一虚拟环境墙钟。生产部署须另外验证可信时间来源、节点间偏差和持续健康状态。
3. 时间不健康时必须保持拒绝：不把审批时间改成提交时间，不篡改历史时间，不给已过期租约追加宽限，也不凭历史回执恢复当前执行权。权限、批准、版本及fence仍需当前验证。
4. 时间源与健康策略应作为部署前置条件，和数据库/模块身份、当前IAM、运行审计分别验证。当前新增的是验证工具中的观测，不是已完成生产ClockHealth模块或Bootstrap集成。
5. 恢复后须重新取得当前权限；过期任务按已有新attempt/fence及稳定效果查询流程处理，不能自动强制重试unknown效果。稳定窗口下仍需完整PG及相关回归重新通过。

这些要求不会自动修正宿主时钟或关闭其他工作。本轮没有调整宿主同步、重启WSL、延长业务20/30秒预算或逐目标租约。
