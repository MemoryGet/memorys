# 可替换排名融合与来源轨迹 V1

本规范细化Fuser端口及ROUTE-02/EVIDENCE-01，首个进程内实现为pkg/fusion.RRF。接口仍为FuseRequest→Candidates，融合不验证权限、发布、引用真实性或模型效果；前后均由查询应用执行相应检查。

## 1. 排名语义

采用按路线排名的RRF：每个证据的分数为所有有效路线的`1/(k+rank)`之和。算法依据[原论文](https://doi.org/10.1145/1571941.1572114)；论文试验结果不代表本系统中文业务效果。k由不可变策略显式提供，不从供应商原始score决定权重。

内部使用精确有理数比较排序，输出Score才转换float64；路线按ID排序处理，同分按平台来源键稳定排序，因此并发到达顺序不会改变结果。输入rank必须正、严格递增且≤1000，可以保留过滤后的排名空缺；重复证据占据实际排名位置，不移除后重编号来增加贡献。输出按融合结果重新连续编号，ScoreKind=rrf。

来源键包括KB、Chunk及完整citation/anchor。相同来源键但不同正文拒绝，不能随便挑一份内容；相同文字不同来源不合并。一个跨Block Chunk仍由适配器拆成可分别引用的Candidate，不能让融合猜位置。

## 2. 防重复放大

同一路线的相同列表重复交付只贡献一次；同RouteID携带不同列表拒绝。多个KB的分区结果须由协调器先形成该路线的全局排名/预算，不把每个KB当成新的加权路线。同一证据在同一路线多次出现，仅首次最佳rank计贡献；同一复合混合列表不能被复制成向量和关键词两份再融合。

每条真实独立路线可各贡献一次，这是预先配置的融合策略，不是由后端随意增加RouteID。基础RRF函数只负责算法；下述ProfileRRF已绑定独立路线库存。真实性仍由受控配置及认证调用链提供，字段ID匹配不能识别冒用同名身份的攻击者。

## 3. 多路来源的契约补齐

Candidate原来只有一个RouteID/RetrieverID，不足以保留所有融合来源。新增可选FusionOrigins，逐项记录RouteID、RetrieverID、原rank及GenerationIDs；Candidate.GenerationIDs保留所有路线的并集。顶层RouteID/RetrieverID是确定性代表，不表示融合仅使用该路线。来源轨迹不进入公开citation，供平台追踪和重排请求使用。

原始Retriever不得输出FusionOrigins；平台融合结果也不重新作为原始路线投票。重排wire校验每个origin路线唯一、rank及ID合法、代际完全覆盖Candidate的并集，拒绝伪造/缺失代际。新版Go编解码和modules.v1 Schema支持该可选字段，已有旧请求无字段仍通过。

这属于V1未冻结草案的增量，不能假定旧严格远程实现接受新增字段。正式装配使用轨迹的远程重排器须先通过字段兼容验收；厂商协议由适配器转换，但平台侧保留完整轨迹。当前没有实际后端/版本协商或注册工厂证明。

## 4. 预算和错误

首实现最多32个输入列表、每列表1000项、累计10000项及16MiB候选正文；重复列表同样占输入处理预算。k为1至10000、Limit为1至1000，要求有限请求deadline并与调用context取更早者。循环与返回均检查取消；纯排序/JSON处理不能硬抢占，计数和已验证DTO/来源消息预算共同限制工作。不是生产延迟保证。

候选正文UTF-8、平台身份、代际、有限原始分数及排名验证失败则静态ErrInvalid，不回显输入。输出嵌套citation/代际和来源轨迹复制，不与输入共享可写切片。算法不调用外部服务、不写数据库或索引，也不放宽现有权限检查。

## 5. 证据与未通过项

4项Go测试覆盖分数尺度隔离、精确同分及顺序稳定、多路来源/重排wire往返、重复路线和重复候选不增加贡献、正文冲突、再融合拒绝、参数/取消及输出副本。2项Python试验包含独立Schema及实际Go DTO往返，另拒绝重复来源、缺/外部代际和原检索器伪造轨迹。见[执行证据](evidence/fusion-review.json)。

尚未验证获准路线库存、实际多个KB协调/候选全局预算、真实OpenSearch/Qdrant或WeKnora检索、来源真实性、当前授权、参考实现替换、完整性能和Recall@10≥90%。RRF只是首个可替换Fuser实现，不能据此关闭ROUTE-02、阶段D/F或整体架构验收。

## 6. Pipeline/QueryProfile绑定的融合实例

`NewRRFForProfile(pipeline, query)`实现同一Fuser端口，捕获Pipeline/Query的ID、版本、摘要及路线策略；核对引用版本相同、FusionMethod=rrf、k/全局候选预算有效、路线唯一、检索/复合模块能力和实例ID、每路预算之和不超过全局预算。结构检查不重算完整Profile摘要、不验证其来源，实例应由正式归一化/工厂取得已核验配置后创建。

请求必须绑定捕获的PipelineDigest、rank常数与受限Limit；只允许声明路线和指定RetrieverID，每路结果数量及全部输入数量均受配置预算约束。必需路线必须显式提供列表，零候选合法；可选路线可以缺席，但降级原因仍由查询协调器记录，不能凭缺席列表判断是无结果还是服务失败。重复列表也占输入处理预算，不能靠去重后数量掩盖处理成本。

多个KB的子请求共享路线配额，需先合并为该路线的全局排名；当前尚无真实跨KB协调器。配置中的可选图谱和记忆不可自动成为新路线投票，只有捕获的ID可贡献。来源正文、发布/权限、服务身份和有效代际仍在融合外核验，RetrieverID字符串匹配不是身份认证。

构造器复制所需路线/策略，原QueryProfile的slice/map后续改变不影响实例；Identity返回固定引用与摘要。更换QueryProfile或Pipeline必须创建新实例，请求不能通过修改k、增加路线或提高Limit进行隐式策略切换。旧实例不监听配置更新，实际装配/重启和持久配置核对尚未实现。

新增4项Go检查覆盖必需/可选/空结果、注入路线/冒用实例/摘要及策略变更、路由分配/全局预算、Profile引用版本和输入配置修改隔离。见[执行证据](evidence/fusion-profile-review.json)。这推进ROUTE-02局部策略验证，未完成受信Profile来源、工厂/获准提供方、真实多KB调度、后端过滤、替换或Recall验收。

## 7. 受控模块装配与重启边界

`NewRRFModule(pipeline, query)`返回kernel.Factory和必要settings，固定提供方platform.rrf/实现1.0.0，只暴露Fusion端口。捕获不可变ProfileRRF；settings仅接受单个profile_identity字段，值为所捕获Identity的Go JSON SHA-256。该摘要是本地装配身份标记，不是跨语言Profile内容摘要或真实性证明。配置中的标记与工厂捕获身份不符时，预检和直接Create均拒绝；重复、缺失、大小写错误、未知字段和尾随JSON均拒绝。

装配摘要包含settings，因此更换Profile的ID、版本或摘要会改变配置版本；它不重新验证原始Profile内容是否符合声明摘要。正式配置归一化与可信来源仍是前置门槛。当前一个工厂固定捕获一个Profile，多个Profile实例须由后续受控工厂目录按实例管理，不能把本次实验当作完整多知识库装配。

每次Create生成独立生命周期包装，启动健康检查确认context和开放状态；这是无外部连接的本地健康检查。Close幂等；关闭后新查找及保留旧引用的新调用均拒绝。主机须先排空进行中的调用，再停止/重启；已进入Fuse的请求不因Close强行中断。本地算法无持久状态或资源句柄需要迁移。

3项实际Go检查覆盖注册/解析端口/调用、配置更换并重建runtime、摘要变化、停止旧引用、错配置和独立生命周期。全Go回归和vet通过，见[执行证据](evidence/fusion-module-review.json)。这是同一实现的新Profile重启试验，没有第二种算法、实际后端、生产配置加载、实时授权或性能/召回证据，ROUTE-02及整体验收保持开放。
